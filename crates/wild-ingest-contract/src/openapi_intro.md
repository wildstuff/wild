The door a program outside the Wild daemon, a **producer**, sends closed records through. This page calls that program a producer throughout; where an answer names its paired install — `device` in the key's answer, `POST …/device/epoch`, a row's lineage — it means the same producer's install, which the operator's app shows as their connection.

## Where the door is

A producer on the operator's machine reaches the door over the socket `system/ingest.sock` in the operator's profile. Over TCP it takes a **pairing file**, which Wild writes when the operator pairs it (`PairingFile` among the schemas): one JSON object with the door's address (`door`), the fingerprint of its certificate (`door_certificate`, absent for an `http://` door) and the one-time pairing code (`pairing_code`). Wild writes it readable by the operator's user alone, so the code never passes through a prompt or a chat. Take the file's path as configuration, e.g. `--pairing <file>`, never its contents, and never print or log the code.

Read the file at your first start. Keep the door and its fingerprint with your key, announce yourself with the code, and remove the file only once your state holds the announcement — the key and its epoch. Do not remove it earlier: until the poll has handed the key over, the code in the file is the only way in. The code is valid for ten minutes and opens one announcement; for as long as it holds, it opens an announcement in your place. A later start, with the same command, finds no file and takes the door it kept.

- `http://` for a door on this machine only: on loopback, or at `10.0.2.2`, where a virtual machine under QEMU user-mode networking reaches its host's loopback. Plain, no certificate, no fingerprint. Refuse an `http://` door at any other address — plain HTTP carries the pairing code and the key in the clear — and never send to it.
- `https://` on the local network: TLS only, with a certificate the Wild made itself, which no certificate authority vouches for. **Pin it.** The fingerprint has the form `sha256:` followed by 64 lowercase hex digits: the SHA-256 of the certificate's DER bytes — the end-entity certificate the door shows first in its TLS handshake, not its key and not its PEM text. Trust exactly the certificate whose fingerprint that is: compare the SHA-256 of the certificate the door showed with the pin before you write a single byte over the connection, and send only when they are equal. Where your TLS library lets you, do the comparison inside the handshake, in a custom certificate verifier, so the handshake's signatures are checked against that certificate; where it does not (Python's `ssl`, Node's `tls`), complete the handshake without certificate-authority verification, take the peer's certificate in DER, compare, then send. Never trust the door any other way: not by a certificate authority, not by its name — the certificate's name is not the address you dial, so do not check it — and never send with the comparison skipped. A door that shows another certificate is not the Wild you were paired with, or its certificate changed: refuse, send nothing — not the pairing code, not a batch — and say so. Never retry it over `http://`: the door's port speaks only TLS, and a plain request carries the pairing code in the clear. An `https://` door given without a fingerprint is refused the same way.

The key the operator's yes hands over begins `wdk_` and opens one more door at that same listener: MCP, at its own address with `mcp` after it — `https://<door>/mcp` for the TLS door — where the key lands as the connection of its tribe and reaches that tribe's own domain tools, the `atlas_*` reads of its types and the commands it declares, and nothing host-level. Wild's other MCP door, the one the operator's own tools use, answers that key `missing or invalid bearer token`.

## The road

1. **Announce.** `POST /producers/announcements` with your manifest: your sources, the shapes each sends, their fields, and what each of them means. Over the TCP listener the request carries the pairing file's code in the `wild-pairing-code` header; on the local socket it needs none.
2. **Wait for the operator.** Poll `GET /producers/announcements/{announcement}`. It reads `pending` until the operator says yes. While Wild makes your sources ready it answers `503` with the reason in `params.reason`; poll again. Once ready, the answer hands over `producer_key` and `epoch` exactly once: keep both. Two states end the wait for good: `rejected` (the operator declined) and `revoked` (the operator cut this connection off, before or after it fetched its key). On either, stop polling and stop sending; only a new announcement the operator lets in again pairs this install anew.
3. **Take the vocabulary.** `GET /tribes/{tribe}/producers/{producer}/vocabulary` with `Authorization: Bearer <producer_key>`: once at every start, before your first batch. It answers the project and customer names an approved device matches window titles against, with an `etag` naming that copy; keep the `etag` with your state. The door tells a device its copy has gone stale only if it fetched one: a later reply says `vocabulary_changed` to it only after it has asked here at least once, so a producer that never asks can never be told to ask. On a later start send the `etag` you kept as `If-None-Match`: `304` says the copy you hold is still the one served, and `200` hands over the new one.
4. **Send.** `POST /tribes/{tribe}/producers/{producer}/sources/{slug}/batches` with `Authorization: Bearer <producer_key>`, one NDJSON line per record: `{"shape": "name@version", "record": {…}}`. `{tribe}` is the `tribe` the poll answered with your key, the one the operator chose — never a name of your own; keep it with the key. `{producer}` and `{slug}` are your manifest's. Send the highest commit mark you have stored in the `wild-commit-mark` header (absent means 0): each `202` answer carries the connection's mark after the batch, so record the mark with the batch. File every answer with its batch, and on every start consult those answers before you read your data again: a batch answered `202 received` is Wild's durably — drop it from the outbox and never send it again. Its content and mark still stay archived as long as your storage allows, because if Wild is restored from a backup it answers `daemon_rewound` with a `known_mark`, and you send again exactly the batches above that mark. A batch sent again after a lost reply is recognised by its id and answered from the receipt: that is the one case in which sending twice is harmless, and only while the answer is missing. A batch whose answer says it was not taken — a refusal, a `429`, a `503`, a state you do not know — stays kept and is re-posted, that same batch, never a rewritten new file. `503 paused` means the operator paused this connection: nothing was received, so keep the batch and send it again after `Retry-After`. Your key still opens the door, and the status route's `paused` directive says when the pause ends; once the operator resumes you, the same key delivers again — no new pairing, no new key, no new epoch. A paused connection is never `401`: that answer is a revoked key.
5. **Ask for its state.** `POST /tribes/{tribe}/producers/{producer}/batches/status` with the batch ids. A batch moves from `received` to `processed` or `failed`; `conflicts` name the lines Wild did not take as sent. States are information: never re-send because of one. A batch Wild removed with its rows, because its source's retention ended or the operator erased it, reads `expired`: drop it if you still hold it. A re-send of it is answered `expired` and writes nothing. A `202` also carries `pending`, the states of your oldest batches the door still holds, each with any per-line `conflicts`; a refusal names its refused lines in `rejected_lines`. The producer status Wild shows the operator adds `delivered.lines_refused`, the count of lines it did not take, and marks a shape no table takes yet with `waits_for_model: true` — its records wait at the door until the operator models the shape, and nothing is lost meanwhile. Follow the `directives`: `new_epoch`, `vocabulary_changed`, `paused`. `vocabulary_changed` says the copy of the vocabulary you hold is no longer the one the door serves: fetch the vocabulary again (step 3). It reaches only a producer that announced `needs_vocabulary: true` and has fetched the vocabulary at least once, and fetching the current copy stops it.

## Where your records land

Every shape lands in a table of the tribe's domain model. When the operator activates you, a shape the model does not take yet gets a table of its own, named after the shape's `target_type`, each field onto the field of its own name. The operator may map a shape into another table instead, now or later. Your records never overwrite a field the operator maintains. Shapes that share a `target_type` share its table, so they declare a field of one name alike. An announcement whose activation would be refused, such as one where they do not, reaches the operator with the reason and no yes.

## Describe what you send

Give every source, shape and field a `description` in the operator's words: its meaning, its unit, an example. Wild carries a field's description onto the table's field, and the operator and Wild's assistant map and explain your data from it. `cost` says too little; "Estimated cost of the session in US dollars, e.g. 0.42" says enough.

## Keys and history

Send closed records only: a finished span, a settled measurement, never a running total you would rewrite later. The shape's `key_class` says what identifies a record:

- `natural` — the shape's own key fields;
- `position` — an append-only file's generation and byte offset, in `_generation` and `_offset`;
- `live` — your install's epoch and a counter, in `_epoch` and `_seq`.

Wild prefixes every id with your connection's id — the `device` of an answer, `dev-…`. A record sent again under its id with other values is refused (`source_rewrote_history`), and the first values stay. Send each record once: a record sent again unchanged in a later batch is taken, but stored again as a new version.

## Versions

A shape you change is a new version (`name@version`): the door takes only the versions the tribe binds. Additive only within a contract version: a client ignores fields it does not know, and treats any code or state it does not know as "not received: keep the batch and back off".

## Prove it with the kit

`wild-kit` serves this door on a sandbox profile that holds no operator data, and its yes to your announcement is automatic. `wild-kit run` runs your producer through the kit's scenarios and prints one line per check, `PASS` or `FAIL`, with what went wrong in words:

```
wild-kit run --dir /tmp/wild-kit-run -- ./my-producer --pairing '{pairing}' --data-dir '{state}'
```

The kit fills the placeholders for each scenario: `{pairing}`, the path of a pairing file naming the door over loopback TCP, or `{socket}` (the door's socket), `{state}`, an empty directory of your producer's own for its key and outbox, and optionally `{source}`, an append-only file of text lines the kit writes for a producer that reads a `position` source, `'{feed}'`, a file of the lines you hand the kit with `--feed <file>`, which it hands your producer a few at a time before its starts — in `late-yes`, the scenario that holds the operator's yes back, before the one start it gets — and `{keys}`, a directory for your key alone, if your producer keeps it apart from its state — the kit never writes it, only copies it with the state, and after a `rotate_key` the key file your producer reads must hold the new key, since the start after the rotation presents that one. The kit writes the pairing file as Wild does, owner-only, at that machine's first start and after it lost its key, each time with a fresh code; at every other start it is as your producer left it. A producer that announces itself again on a restart is refused, as the real door refuses it, and one that leaves the file behind once its announcement is made fails `received`: its code lies readable on disk. The file names a plain `http://` door and no fingerprint, except in the two scenarios of the door's certificate below. Each scenario starts your producer from nothing on a fresh sandbox, lets it run until it exits or stays quiet for `--patience` seconds (default 5; quiet means not asking the door: announcing, polling for the yes, sending a batch and asking a batch's state all count as activity, and so does a wait the last answer told it to keep), and starts it again on the same state, as a restart would; between starts the file scenarios write, truncate, copy and restore `{source}` and your state. Run it on fixed, synthetic input of several batches: the kit compares what your producer sends under each answer with what it sends on a clean run. The kit hands over the same epochs in every scenario, so a `live` record sends the same line each time.

The scenarios answer the first send of every batch:

- `received`, the door's own answer: every record reads back once with its batch as its lineage, nothing answered `received` is sent again, and your batches sent again in reverse order write nothing;
- `unknown`, a state this contract version does not know, `413`, `422 batch_refused`, `422 shape_version_undeclared`, `429` and `503` with `Retry-After`, `503 paused` (the operator paused the connection) with `Retry-After`, and a refusal code it does not know: every line comes back, no sooner than `Retry-After`, and is received;
- a reply lost after the door received the batch: the same batch comes back and is answered from its receipt;
- `processed` with every conflict code, `failed`, and `expired`: nothing comes back, and your producer sends the same lines as on a clean run;
- a reply lost after the flow had `processed` or `failed` the batch: the same batch comes back, is answered from its receipt in that state, and writes nothing;
- `received` with a directive: `paused` for 2 s (no batch goes out until a reply, the status route's included, stops saying it), `rotate_key` (every later request presents the new key), `send_interval_secs: 1` (batches go out at least a second apart), `new_epoch` (every `live` record made afterwards carries it) and `vocabulary_changed` (a producer that announced `needs_vocabulary: true` and fetched the vocabulary at its start is told the copy it holds is stale, and fetches again; one that announced `false` owes no fetch and gets that check as `SKIP`). A directive arrives during a run, and the kit hands your producer no new lines while it is running: to be measured, it must make one more request in that same run — a batch (a retry it keeps back, or a loop that keeps reading) for `paused`, `rotate_key`, `send_interval_secs` and `new_epoch`, or the vocabulary fetched again for `vocabulary_changed` — or the check is `NOT MEASURED` and names what it still needs. Apart from that, your producer sends the same lines as on a clean run;
- your producer killed while a batch is on the way, once before the door saw it and once after it received it: the door receives the same lines as on a clean run, none lost and none doubled.

With `{source}`, the kit also counts the `position` rows (records carrying `_generation` and `_offset`) against the complete lines it wrote:

- a truncation in place: the lines written after it come under a new generation, and none is lost;
- a half-written last line: nothing is sent before its newline, and the whole line arrives once;
- a whole-machine restore (`{state}` and `{source}` back from a copy) and a rollback of `{source}` alone: nothing is lost or doubled, your producer re-sends nothing it had sent, and a restored copy takes the `new_epoch` the door hands over after its `live` record collides.

Your producer's identity, and a rewound Wild:

- re-pairing: `{state}` and `{keys}` are emptied, as a reinstall does, and your producer pairs again. It reports the fingerprint it first paired with, the door's question offers to continue its connection, and the kit answers „Als denselben Rechner fortsetzen"; what it reads again lands on the ids it had, so nothing is written twice;
- a cloned machine: a second copy of your producer starts on a state of its own while the first holds a live key. The question proposes „neuer Rechner"; the kit gives the other answer, which revokes the first key. Answered `401`, the first copy asks its announcement, reads `revoked`, and sends nothing more;
- a lost state with a kept key (only with `{keys}`): `{state}` is emptied, and your producer asks `POST …/device/epoch` before its first `live` record and takes that epoch; nothing is written twice;
- a Wild restored from a backup (only with `{source}` or `{feed}`): the sandbox comes back from a copy taken one batch earlier. Your producer's next batch presents its `wild-commit-mark` and is answered `daemon_rewound`; it sends again what Wild received above `known_mark`, and every record it lost reads back once;
- a Wild restored from a backup that holds only part of your connection's receipts (only with `{source}` or `{feed}`): the receipt of one batch in the middle is gone and those above it stay. Your producer's next batch is answered `daemon_rewound` with `known_mark` just below the gap and `live_held`, the `live` records Wild still holds above it; it sends again only what was received above `known_mark`, nothing at or below it, and every record it lost reads back once. Below the gap it must have sent at least one record that is not `live` — a `natural` or `position` record — or the kit cannot tell that it sends nothing again and reports that check `NOT MEASURED`, asking for such a record;
- a receipt that expired with its rows (only with `{source}` or `{feed}`): the kit expires the first batch the door received, as a retention or an erasure does, and sends it to the door again, which answers `expired` and writes nothing. Your producer is not told `daemon_rewound`, since the door still knows the mark, and sends nothing of that batch again;
- a producer whose shape is `natural` that loses its state and keeps its key (only with `{keys}`): it reads its source again from the start, and the door answers no `source_rewrote_history` for a record that did not change; nothing is written twice.

The whole-machine restore runs for every producer; without `{source}` it restores `{state}` and `{keys}` alone. Its row count, the truncation, the half-written line and the rollback need `{source}`: a producer that declares a `position` shape but names none gets them as `NOT MEASURED`, and only one that declares no `position` shape gets them as `SKIP`. A producer that declares a `live` shape and sends no `live` record after the restore, after a `new_epoch` directive or after a lost state gets that `new_epoch` check as `NOT MEASURED`; one that declares no `live` shape has no epoch to take anew and gets the three as `SKIP`. Only a producer that declares a `natural` shape is read again from the start; one that declares none gets that scenario as `SKIP`. The cloned machine's first copy, the restored Wild and the expiry need new input between starts, from `{source}` or from `{feed}`: a producer that reads no file is handed one with `--feed <file>` (one record per line, each line a different record — no two compose the same record id under the shape's `key_class`; the kit counts distinct lines, not ids, so it does not check that rule, and it refuses a file with too few). Without either, those checks are `NOT MEASURED` and name both ways. The feed only grows: a restored state reads it on from an older place, and a `natural` record read again lands on the id it had. Without `{keys}`, a lost state is a lost key too, which re-pairing covers: the kept-key scenario is `SKIP`.

The door's certificate (only with `{pairing}`): the pairing file names an `https://` door on loopback, serving a self-signed certificate the kit makes for that scenario alone:

- pinned: the file's `door_certificate` names the door's certificate; your producer pairs over it and its batches are received;
- a wrong pin: the door shows another certificate than the file names; your producer sends nothing over it: not a byte past the handshake, and no connection to the door's port that does not open with a TLS handshake — a plain-HTTP retry fails.

A producer that reaches the door over `{socket}` alone gets both as `SKIP`, since the socket has no certificate.

What the kit does not play it prints as `NOT BUILT`, which is the kit's gap, not your producer's; every scenario above is played. It exits 0 only when every check passed or was skipped. Each scenario's sandbox and your producer's output stay under `--dir`; `wild-kit rows --dir <dir>/<scenario>/sandbox` prints the rows it wrote.
