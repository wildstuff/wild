# `cash-forecast` — the ADR-0202 dogfood Procedure

A seasonal cash-inflow forecast: the thinnest artifact that exercises the
whole model chain (build → pin → declare → gate → store → describe), and the
reference every later Procedure copies.

**Vocabulary (ADR-0202 D4).** The machinery word is `procedure`; to an
operator it is a **Procedure** (German: *Verfahren*), and its output is a
**Prognose** / **Schätzung**. `method` is the sentence on the card. An LLM
is an **Adapter** and never appears here.

## What it answers

> Erwarteter Zahlungseingang zum 05.02.2025: **rund 45.100 €** — Schätzung
> aus Verfahren *cash-forecast* (Stand v4, Güte MAPE 0,0353).

Two doors onto one model:

| Door | Name | Who uses it |
|---|---|---|
| `wild:function/backing` | `cash_forecast` | a declared field, via `backed_by: cash_forecast` (ADR-0082) |
| `wild:tool-provider/tools` | `cash-forecast` | an operator or Elder, directly |

Both call the same `procedure::forecast`, so a hand check and a stored estimate
cannot disagree.

## Why it imports nothing

A fitted model carries its parameters, so it needs no clock, no socket and
no lake read. That is what keeps it inside the **ADR-0202 D10.3 determinism
profile**: re-running v4 over the same inputs has to answer the same number,
or the audit trail is a story rather than a record.

The built component's actual imports — the measured floor the Rust standard
library links into every component, and nothing beyond it:

```
wasi:cli/{environment,exit,stdin,stdout,stderr,terminal-*}
wasi:clocks/monotonic-clock
wasi:io/{error,poll,streams}
```

`wild:function/backing` and `wild:tool-provider/tools` are **exports**, not
imports; the profile constrains what a Procedure may reach for, not what it
offers.

## The audit card is measured, not claimed

`procedure.yaml` is the ADR-0202 D4 manifest. Every number in it is re-derived
by tests from the training extract it names:

- `the_baked_parameters_are_the_fit_of_the_shipped_extract` — re-fits the
  baseline and all 52 weekly factors from
  `training/inflows-2023-2026.csv`, and fails if one drifts;
- `the_manifest_holdout_score_is_the_measured_one` — recomputes the MAPE
  the card claims (0.0353) over the held-out fourth year;
- `the_audit_card_states_the_parameters_the_component_actually_uses` — holds
  the card and the constants to EACH OTHER. The first two check the code;
  the card is what the auditor is handed, and it carried the same 52 numbers
  a second time by hand.

D7.2 asks that an auditor be able to re-check a Procedure with a
spreadsheet. Those three tests are that spreadsheet, run on every build.

### Checking it by hand

```
expected_inflow = 42068.98 × factor[week_bucket]
```

Weekly buckets are counted from the epoch Monday **2023-01-02**; the factor
table is in `procedure.yaml` under `parameters.seasonality`.

## The training extract

`training/inflows-2023-2026.csv` — 208 weekly inflow totals. The first 156
weeks (2023-01-02 … 2025-12-22) are the training window; the final 52 are
held out for scoring. It is **synthetic**, generated by
`training/fit.py` from a documented formula plus a fixed-seed LCG, so anyone
can regenerate it byte-for-byte and re-derive the same coefficients. That
script also prints the parameters baked into `src/procedure.rs`.

Its sha256 is what `procedure.yaml`'s `source_ref.digest` pins.

### Superseded versions stay re-derivable

`fit.py` carries one entry per REGISTERED version and they never leave:
`python3 training/fit.py v3` rewrites `inflows-2023-2025.csv` byte-for-byte
and prints v3's baseline (42308.60) and MAPE (0.038). A stored estimate that
claims v3 produced it has to stay checkable for as long as it stands — the
training-time half of the re-run door (ADR-0202 D7.3).

The window is one law walked with one seed in one order, so a longer fit is a
SUPERSET of a shorter one: the first 156 rows of v4's extract ARE v3's
extract. v4 is a year more of the same business, not a different world drawn
under a new name — which is what makes the v3-vs-v4 gap a statement about
estimation noise rather than about the data.

## Dates

`target_date` is the date the estimate is **about** (`as_of` + horizon),
never the run date — ADR-0202 D3's valid-time anchor. This is what lets a
dated chart over the stored estimates answer *"was sagte die Prognose zum
31.03.?"* instead of refusing.

## What it refuses

- A horizon beyond **365 days** — a seasonal fit over one year of buckets
  says nothing useful past that, so it refuses rather than answering
  confidently and wrongly.
- A date it cannot read (`as_of` must be ISO `YYYY-MM-DD`).

Both are the caller's to fix, so both come back as `invalid-args` rather
than entering the host fault net.

## Build

```bash
bash plugins/scripts/build-wasip2-component.sh examples/tool-providers/cash-forecast
cargo test    # from this directory — the model + door tests
```

`wit/deps/` holds committed symlinks into the canonical `wit/` tree. There
is deliberately no symlink into `wit/external/`: this component imports no
`wasi:*` package directly, so it needs no `wit-sync` and cannot trip the
`hashFiles` symlink hazard that bites components which do.
