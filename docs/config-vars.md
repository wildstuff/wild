# Configuration Variables — Canonical Inventory

This document is the single source of truth for every environment
variable read by Wild's runtime. It exists to satisfy ADR 0004
(Configuration Injection): every variable here either flows through
`wild_runtime::RuntimeConfig` or is explicitly excluded.

**Rule:** new code must not call `std::env::var("WILD_…")` outside
`crates/runtime/wild-runtime/src/config.rs`. The CI lockdown step
(see `.github/workflows/ci.yml`) enforces this.

## Section 1 — `WILD_*` application configuration (flows through `RuntimeConfig`)

These vars map onto fields of `wild_runtime::RuntimeConfig` (or one
of its sub-structs). Production code reads the field, not the env;
where the Config-field column names a `*_from_env` seam instead, that
static read on the sub-struct IS the sanctioned parse (a struct field
would collapse the presence-vs-default distinction the seam exists to
keep). Tests construct `RuntimeConfig::for_test_with(|c| …)` overrides.

| `WILD_NATS_URL` | `nats://127.0.0.1:4222` | `cfg.nats.url` | `NatsConfig` | NATS broker the host connects to. | `WILD_MESSAGING_ALLOWLIST_ENFORCE` | unset (false) | `cfg.nats.allowlist_enforce` | `NatsConfig` | ADR-0062 (one gate) — posture of the guest-publish **capability allowlist** check. Default (unset/`0`) = **shadow**: an in-tribe publish outside the role's allowlist is allowed with one WARN naming the miss. `1`/`true` = **enforce**: an allowlist miss denies the publish. The e2e fixture suite (`xtask tribe-e2e`) runs with `WILD_MESSAGING_ALLOWLIST_ENFORCE=1` so every merge proves the rendered allowlists cover the fan-out architecture's real publishes; the default remains shadow for existing operator installs until a separate one-line flip PR is approved. | `WILD_FORGED_BUNDLE_URL` | unset (host toolchain) | `ForgedConfig::bundle_url` | `ForgedConfig` | Where the ADR-0260 D5 toolchain bundle comes from: `oci://` (ghcr artifact), `https://` (direct), or `file://` (air-gapped installs whose package embeds the tarball). Unset → the host's own toolchain (dev mode: builds run `--locked`, online). Set → builds run `--frozen` against the bundle's vendored allowlist set, fully offline. |
| `WILD_FORGED_BUNDLE_SHA256` | unset | `ForgedConfig::bundle_sha256` | `ForgedConfig` | sha256 (64 hex) of the bundle tarball — MANDATORY beside `WILD_FORGED_BUNDLE_URL` (digest-pinned by design; a URL without a digest is a startup refusal, never trust-on-first-use). `xtask forge-bundle-publish` prints it; the repo records it in `forge/bundle/manifest.toml` `[published.*]`. A digest already installed under `<work_dir>/toolchains/` is reused without network — a held toolchain keeps working offline, and changing the digest IS the update. |
| `WILD_FORGED_RECEIPT_KEY` | unset (no receipts) | `ForgedConfig::receipt_signer` | `ForgedConfig` | ADR-0267 D7 — the receipt signing key: a 32-byte Ed25519 seed as 64 hex chars (the install-identity key conventions). Set: every green build returns a builder-signed receipt (Wasm custom section + response field) binding artifact digest (receipt section excluded), install key, slot id, builder identity, toolchain-bundle digest, timestamp and the D11 admission voucher — which the same key also signs. Unset: builds succeed with NO receipt minted, the pre-hosted-launch posture. Present but unparsable: startup refuses BY NAME — a signing server quietly degrading to unsigned would be indistinguishable from the intentional unset. The matching public key (logged at startup) is what daemons pin via `WILD_FORGE_RECEIPT_VERIFYING_KEY`. |
| `WILD_FORGED_TOOLCHAIN_ROOT` | unset | `ForgedConfig::toolchain_root` | `ForgedConfig` | A toolchain tree ALREADY on the filesystem, mounted by whoever booted the server — no fetch, no unpack. The ADR-0260 D2 guest carries its toolchain on a read-only squashfs disk rather than inside the initramfs, because an initramfs is unpacked into RAM and stays there (measured 2026-08-18: that cost 2,600 MiB resident and a 10.3 s boot; a mounted disk costs 297 MiB and 2.3 s). No digest is checked here — the HOST verifies the disk image's sha256 from `boot.json` before attaching it. The layout IS checked, so a disk that failed to attach refuses at startup by name instead of surfacing as a compile error inside a build. Takes precedence over the bundle path; setting both is a named refusal. |
| `WILD_FORGED_BUNDLE_DISCARD` | unset (false) | `ForgedConfig::bundle_discard` | `ForgedConfig` | Delete a `file://` bundle once it is installed and digest-verified. For the ADR-0260 D2 guest image, whose whole root filesystem is RAM, this frees the ~308 MiB tarball that would otherwise sit beside the ~1 GiB tree it was unpacked into. Safe against restarts: an installed digest short-circuits before the URL is read. It buys steady-state headroom, NOT a lower boot floor — the peak is the unpack, where both copies coexist. Off by default; a self-hosted install on real disk wants its tarball kept so a reinstall after clearing the state dir still works offline. |
| `WILD_FORGED_CERTIFICATE` | unset (open policy) | `ForgedConfig::certificate_path` | `ForgedConfig` | ADR-0267 D9 — path to this builder's certificate: the JSON `BuilderCertificate` that `xtask forge-cert-issue` signs with the root key (org, builder key, validity window, slot pool, grace period). Set: the server boots the certificate-backed entitlement policy — the slot ledger lives beside `WILD_FORGED_WORK_DIR` (`entitlement-ledger.json`), new slots count against the cert's pool, known slots rebuild freely, retire frees. Startup verifies the file against the COMPILED-IN root key and refuses BY NAME on an unreadable/unparsable file, a signature that does not chain, a window already past grace, or a `builder_key` differing from `WILD_FORGED_RECEIPT_KEY`'s public half (the D7 chain coherence — a certified builder signs receipts under the certified key, which also means `WILD_FORGED_RECEIPT_KEY` is REQUIRED beside this var). Past expiry but inside grace: builds keep admitting and every accepted answer carries the countdown; a not-yet-open window refuses naming the clock, never a renewal. Admission is two-phase (a refused or malformed submit consumes no slot), NEW claims require a signed request, a shrunk pool freezes newest slots first (D3 coverage: running untouched, rebuild refused `frozen: true`), a `parallel_build_lanes` grant caps `WILD_FORGED_MAX_PARALLEL`, and an OS lock pins the ledger to ONE server process. The root key is deliberately NOT env-overridable — that would re-root the chain with one variable. Unset: the open launch policy. |
| `WILD_FORGED_TEST_POLICY` | unset | `ForgedConfig::test_policy` | `ForgedConfig` | ADR-0267 D5 — boots the server with a named TEST entitlement policy (`deny-all`, `require-identity`, `slot-ceiling`) so the refusal paths can fire end-to-end against the real binary. Honored ONLY when the non-default `test-policies` cargo feature is compiled in (e2e builds); a binary without the feature — every release build — refuses to start when the var is set, never a silent open-policy fallback. |
| `WILD_FORGED_MIN_DAEMON_VERSION` | unset (no gate) | `ForgedConfig::min_daemon_version` | `ForgedConfig` | Operator-set minimum Wild release version (`x.y.z`; a leading `v` — the git-tag shape — is tolerated) a daemon must run to drive the MUTATING routes (submit AND retire; the read-only status/artifact polls stay ungated so an already-admitted build can finish). Every daemon identifies its release version and OS/arch on the wire via the advisory `x-wild-daemon-version` / `x-wild-daemon-os` headers (outside the install signature — operational metadata, not authorization); when this floor is set, a request whose version header parses BELOW it is refused `incompatible-client` (HTTP 426 Upgrade Required) with a message naming both versions and "update Wild". Refusal on positive evidence only: a request with NO version header (a legacy daemon predating the headers) passes, and an unparsable or non-ASCII header warns and passes — telemetry never bricks a build by absence or malformation. A present-but-unparsable FLOOR, by contrast, refuses STARTUP by name (the `WILD_FORGED_RECEIPT_KEY` precedent — a gate the operator set that silently guards nothing would be indistinguishable from the intentional unset). Comparison is on the `(major, minor, patch)` coordinates only (the shared `wild-release-version` parser), which is a deliberate trade-off: prereleases of the floor version pass — `0.5.0-rc.6` passes a `0.5.0` floor; to exclude them, set the floor one patch higher. |

### Skip-flags policy

`WILD_SKIP_*` flags exist for development and integration testing.
In **release builds**, `RuntimeConfig::from_env` logs a warning at
boot when any skip-flag is set, but honours the flag (staging
environments routinely use release builds with skips). The warning
makes accidental production use visible in logs.

### Profile lifecycle

`WILD_PROFILE` is read once at process boot (per ADR 0004 §Phase 0
decision). Profile switching requires a restart. A future ADR can
introduce hot-reload via `Arc<RwLock<RuntimeConfig>>` if the
product needs live profile-swap.

`WILD_NATS_TOKEN` is why `nats.conf` carries no secret: the
`authorization` block references the var, the conf stays shareable, and
token rotation only rewrites `system/token` (the next broker start picks
it up). Mechanism works identically on macOS/Linux/Windows — nats-server
does the expansion itself.

`GITHUB_TOKEN` is intentionally read at point-of-use — it's an auth
secret pulled fresh per network call, not declarative config.

`WILD_TOKEN` is the same class: stage 1 of the shared HTTP bearer-token
resolution (`wild-shared/src/auth.rs::resolve_token` — env wins over the
on-disk `system/token` file, which is created on the fly when both are
absent). ONE secret for both transports (MCP + REST). An auth secret, not
declarative config; the env-var name reaches `env::var` through a parameter
so parallel tests can use scratch names. (Renamed from `WILD_MCP_TOKEN` /
`system/mcp.token` — no env alias; the file is migrated on first resolve.)

## How to add a new tunable

1. Add the env name to Section 1 with default + target Config field.
2. Add the Rust field to the appropriate sub-struct in
   `wild-runtime/src/config.rs`.
3. Read the env in that sub-struct's `from_env`.
4. Pass the field into the consuming subsystem via a constructor arg.
5. Reference the new field from this doc.

Do **not**:
- Add a `std::env::var("WILD_…")` call outside `wild-runtime/src/config*.rs`.
- Add a `set_var`/`remove_var` call to non-test code.

## ADR-0165 note

The field-level LLM privacy-scope feature (`llm_scope` / `privacy_tier`)
introduces **no new `WILD_*` environment variable**. Adapter classification
